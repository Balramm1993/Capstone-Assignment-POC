# Design Writeup

## 1. Problem

Given a user story, description, business rules and acceptance criteria, a useful test suite must do more than produce plausible test ideas. It needs explicit traceability, balanced test categories, risk prioritization and evidence that the acceptance criteria have actually been covered.

The core risk is that a one-shot generator can produce many cases while silently missing an important criterion.

## 2. Architecture

```text
Feature specification
        |
        v
+-------------------+
| Requirement input |
+-------------------+
        |
        v
+-------------------+
| Initial generator |
+-------------------+
        |
        v
+-------------------+
| Coverage critic   |----> AC/category gaps
+-------------------+
        |
        v
+-------------------+
| Repair generator  |
+-------------------+
        |
        +---- repeat until no gaps / max iterations
        |
        v
+-------------------+
| Exporter          |
| CSV + Gherkin     |
+-------------------+
```

The implementation has four logical responsibilities:

- **Input:** JSON feature specifications preserving the exact AC IDs.
- **Generation:** pattern-based test generation for the supplied domains.
- **Critique:** maps each case back to AC IDs and checks category coverage.
- **Repair:** creates targeted cases only for the gaps identified by the critic.

## 3. Agent state

Each iteration records:

- iteration number
- current case count
- covered acceptance criteria
- uncovered acceptance criteria
- missing categories for each AC

This state is stored in the generated coverage reports. It makes the iterative behavior inspectable during the demo.

## 4. Prompt/tool design

The offline implementation does not depend on an external LLM. The equivalent of a structured generation prompt is encoded as deterministic templates:

- positive: expected successful behavior
- negative: invalid or prohibited behavior
- boundary: threshold/minimum/maximum/time boundary
- edge: unusual combinations, timing, normalization, state transitions

A future LLM adapter should return structured JSON with fields for acceptance criteria, category, title, preconditions, steps, expected result, priority and risk. The critic should receive the requirements and generated cases and return only structured gaps.

## 5. Traceability strategy

Every test case has an `acceptance_criteria` field. The critic creates an AC → categories map and checks:

- Is every AC represented?
- Does every case use an allowed category?
- Are positive, negative, boundary and edge perspectives represented?
- Are high-risk criteria covered?

The generated CSV is therefore suitable for import or transformation into a TestRail/Zephyr import template.

## 6. Risk model

- **P0:** authentication, pricing, lockout, session, discount eligibility and other business-critical behavior.
- **P1:** important validation, normalization and user-flow behavior.
- **P2/P3:** lower-impact or usability-focused coverage where applicable.

## 7. What broke / how it was fixed

### Potential failure: one-shot generation
A large draft can still miss an AC.

**Fix:** added an explicit critic that checks every AC and repairs missing category coverage.

### Potential failure: duplicate repair cases
A repair loop can repeatedly generate the same case.

**Fix:** maintain an `(AC, category, title)` uniqueness key before adding repaired cases.

### Potential failure: vague traceability
A case can mention a requirement without a machine-checkable relationship.

**Fix:** every case stores exact AC IDs and the critic parses them.

### Potential failure: non-reproducible demo
An external model/API introduces credentials, network dependency and variable output.

**Fix:** the submitted core agent is deterministic and offline. The architecture keeps generation and orchestration separate so an LLM can be added later.

### Potential failure: missing boundary coverage
Typical generation tends to focus on nominal examples.

**Fix:** the critic explicitly treats boundary and edge as first-class categories and the repair stage creates threshold/time/state cases.

## 8. Acceptance criteria coverage

The supplied run produces coverage reports for both features. The reports are generated by the same critic that drives the repair loop, so the coverage report is not a manually typed claim.
